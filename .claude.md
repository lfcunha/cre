# NYC CRE Intelligence Platform — Project Brief

## Goals & Positioning
- Portfolio/credibility project demonstrating AI engineering depth — not primarily revenue-driven, no fixed timeline, self-paced.
- Aimed at future fractional CTO and advisory work.
- Open-source strategy: release the reusable engine (extraction pipeline, entity resolution mechanics, pipeline scaffolding) publicly with technical write-ups.
- Proprietary layer: curated data + resolved entity graph — the eventually-sellable asset.
- If monetized: subscription-based monitoring/alerts on user-defined entity watchlists — not one-off reports or self-serve search.
- No employer conflict — Capital One role is credit card risk, not CRE (worth a due-diligence check of employment agreement language).

## Core Architecture
Data sources → extraction/normalization → entity resolution → knowledge graph → monitoring/change detection → intelligence/API layer.

**First vertical / MVP scope:** NYC commercial real estate, Manhattan commercial and multifamily properties.

### Database & Graph Model
- **Postgres** as system of record for all raw ingested data.
- Property graph model built on top of Postgres (not a separate graph database):
  - **Nodes:** LLC, Person, Lender, Property, Document, Address, Event
  - **Key edge:** `related_to` self-join on LLC — the core entity-resolution moat
- **Entity resolution:** Spark GraphFrames connected components algorithm, run as a periodic batch job, writing `resolved_entity_group_id` back to Postgres. Live product does indexed lookups only — no live graph traversal needed for MVP.
- **Deferred decision:** graph database layer for querying (AGE/Cypher vs. PuppyGraph/Gremlin).

### Orchestration
- **Dagster**, self-hosted (no Dagster+), asset-centric model. Considered switching to Prefect but concluded Dagster models branching/multi-source pipelines better; relearning cost outweighed the benefit.

### LLM Stack (deliberate multi-model design for credibility/comparison)
- **Extraction:** Qwen3.6-35B-A3B or Gemma 4 26B A4B (both Apache 2.0, mixture-of-experts)
- **Summarization/explainability:** Mistral Small 4
- **Serving:** Ollama (local dev), vLLM (EC2 production)

### Neighborhood Assignment
- One-time batch spatial join (BBL lat/long → neighborhood polygon) via GeoPandas as a Dagster asset — not a live PostGIS setup.
- New BBLs handled via a small incremental "unassigned BBLs" asset rather than full re-runs.
- Uses informal/colloquial neighborhood boundaries (matches how buyers actually talk), not just official DCP NTA boundaries.

## Dataset Inventory

**Confirmed / in scope:**
- **Property records:** ACRIS (Master, Legals, Parties, References — covers liens, satisfactions, lis pendens/notice of pendency, fixture filings as document types); PLUTO (includes lat/long per BBL already)
- **Sales & valuation:** DOF Rolling Sales, DOF Assessments
- **Building activity:** DOB Permits, Violations, Certificate of Occupancy, DOB NOW job filings
- **Housing compliance:** HPD Violations, Registrations (useful for officer/signatory data), Litigations

**Distress signals (hardest to access):**
- NYSCEF court filings (no public API, scraping friction)
- NYS Dept of State UCC filings (distinct from ACRIS's real-property fixture filings)
- DOF Annual Lien Sale list

**Deferred / Phase 2 (context layer, not urgent):**
- DCP zoning districts, ULURP applications, BSA variance filings, LPC landmark designations

**Schema note:** Only ACRIS Legals and PLUTO carry a borough field — Master, Parties, and References must be pulled citywide and scoped to Manhattan downstream via `document_id` join against Legals.

## Progress So Far
- Working Socrata API puller script (`pull_acris_pluto.py`) covering ACRIS Legals, Master, Parties, References, PLUTO, and the Document Control Codes lookup table.
- Script design: shared paginated-pull function, offset checkpointing, retry/backoff logic, raw NDJSON landing with pull timestamps, `--since` / `--citywide` / `--no-resume` flags.
- Intentionally mirrors the structure of future Dagster `@asset` definitions.
